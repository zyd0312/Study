# EIP-8079：原生 Rollup（Native rollups）

> **状态**：Draft（草案）｜**类型**：Standards Track: Core（标准track，核心协议变更）｜**作者**：Luca Donno（@lucadonnoh，L2BEAT）、Justin Drake（@JustinDrake，以太坊基金会）｜**创建日期**：2025-11-13｜**原文链接**：https://eips.ethereum.org/EIPS/eip-8079 ｜**讨论帖**：https://ethereum-magicians.org/t/eip-8079-native-rollups/26565
> **一句话结论**：把以太坊自己的「状态转换函数（State Transition Function, STF）」以一个名为 `EXECUTE` 的预编译（precompile）暴露给 L1 执行层，让 EVM 等价的 rollup 不必再自己造证明系统，而是直接复用 L1 的执行验证能力。

> **批注（先说最重要的一点）**：这是一份 **Draft 且大量留空的 EIP**。参数值、预编译的输入编码、返回值、gas 计费、测试用例、参考实现、安全考量——全是 `TBD`。它现阶段的价值是「把设计意图和接口骨架钉在规范里」，而不是「可以照着实现」。如果你带着「native rollup 到底怎么收费、怎么防 DoS」的问题来，这份 EIP **给不出答案**，得回到 ethresear.ch 的原帖去看。

## 这个 EIP 要做什么（Abstract / Motivation 的中文重述）

**Abstract 只有一句话**：通过一个新的 `EXECUTE` 预编译，把状态转换函数暴露给执行层。

Motivation 部分给出了三条动机，值得逐条拆：

1. **重复造轮子的成本与风险**。今天的 EVM 等价 rollup，为了复现以太坊 L1 本来就有的东西，必须自己实现并维护一整套复杂的证明系统（proof system）。复杂度直接推高 bug 概率，也让这些项目摆脱不了「安全委员会（security council）」这个后门，从而卡在 L2BEAT 的 Stage 2 之下。更糟的是，各家 EVM 等价项目彼此又「不够像」，缺乏互相复用成果的激励，导致多证明系统（multi-proof）迟迟落不了地。

2. **治理分叉的问题**。为了跟上以太坊的特性演进，rollup 不得不自建治理系统；而这套治理**无法被强制跟随以太坊的治理决策**，理论上可以任意偏离。EVM 等价 rollup 能做的最好防御，只是给用户留一个足够长的「退出窗口（exit window）」，防治理作恶。

3. **但退出窗口治不了本**。任何有限（且合理）长度的退出窗口，都保护不了所有用例——尤其是依赖时间锁的场景：治理合约、质押合约、归属（vesting）合约。窗口越长保护面越广，代价是「与以太坊不等价的时间」越长。

结论：让 rollup **复用以太坊的状态转换验证基础设施**，从而大幅简化自身基础设施与升级流程，把资源腾出来做面向用户的产品。

**批注**：注意动机的重心不在「省 gas」也不在「更快」，而在**信任假设**和**治理**。native rollup 的卖点是「我不再需要自己的证明系统，也不再需要自己的升级密钥来跟进 L1 硬分叉」。这条线索是理解 2025-2026 年这波讨论的关键——它不是 Optimistic vs ZK 二分法的第三支，而是想把这个二分法整个消解掉。

## 规范要点（Specification）

### 1. 常量参数

| 常量 | 值 | 说明 |
| --- | --- | --- |
| `PROOF_TX_TYPE` | `Bytes1(TBD)` | 「携带证明的交易」的交易类型字节，**原文未给定值** |
| `EXECUTE_PRECOMPILE_ADDRESS` | `TBD` | `EXECUTE` 预编译地址，**原文未给定值** |
| `ANCHOR_ADDRESS` | `TBD` | L2 侧「锚定（anchoring）」预部署合约地址，**原文未给定值** |

### 2. `EXECUTE` 预编译

在 `EXECUTE_PRECOMPILE_ADDRESS` 处新增一个预编译，用于**验证一次状态转换**。原文给出的伪代码语义如下：

```
def execute(input: Bytes) -> Bytes:
    chain = input[...]  # TBD
    block = input[...]  # TBD
    anchor = input[...] # TBD

    transactions = get_transactions(block)

    # 不支持 blob 交易
    for tx in map(decode_transaction, transactions):
        if isinstance(tx, BlobTransaction):
            raise ExecuteError

    block_env = get_block_env(chain, block)

    # 执行锚定
    process_unchecked_system_transaction(
        block_env      = block_env,
        target_address = ANCHOR_ADDRESS,
        data           = anchor
    )

    state_transition(chain, block)

    return Bytes(...)  # TBD
```

逐条读语义：

- **输入**：一段 `Bytes`，在概念上切分为三部分——`chain`（链上下文 / BlockChain）、`block`（待验证的区块）、`anchor`（要注入 L2 的锚定数据）。**三者各自的字节布局与编码方式，原文写的是 `TBD`，未明确。**
- **核心断言**：验证 `state_transition(chain, block)` 成立，即「在 `chain` 上下文中执行 `block` 是合法的状态转换」。
- **禁用 blob 交易**：先遍历区块内所有交易，如果解码出任何 `BlobTransaction`，直接 `raise ExecuteError`。也就是说，**被验证的 L2 区块内部不能再含 blob 携带交易**。
- **锚定（anchoring）**：在正式状态转换之前，通过一笔「未经检查的系统交易（unchecked system transaction）」把 `anchor` 数据发到 `ANCHOR_ADDRESS`，从而在 L2 状态中写入来自 L1 的信息，支撑 L1→L2 消息传递。
- **返回值**：`Bytes(...)`，**原文未明确返回什么**。
- **gas 计费**：**原文完全没有规定该预编译的 gas 成本、定价公式或计费维度**。这是本 EIP 最大的空白之一——一个「执行任意区块」的预编译如何计价、如何防 DoS，规范里一个字也没有。

### 3. 区块头扩展（Header extension）

在现有区块头编码上追加一个新字段：**64 位无符号整数 `burned_fees`**，表示当前区块中作为 base fee 被销毁的原生代币总量。

RLP 编码（原文给出的顺序）：

```
RLP([
  parent_hash, ommers_hash, coinbase, state_root, txs_root, receipts_root,
  logs_bloom, difficulty(0), number, gas_limit, gas_used, timestamp,
  extradata, prev_randao, nonce(0), base_fee_per_gas, withdrawals_root,
  burned_fees
])
```

`burned_fees` 的累计值按下式计算：

```
burned_fees = effective_gas_fee - gas_refund_amount - transaction_fee + blob_gas_fee
```

原文强调：只要把这个值在 L1 上暴露出来，native rollup 就**自动**也能拿到它（因为 rollup 复用的就是同一个 STF）。

**批注**：原文给出的 RLP 字段列表在 `withdrawals_root` 之后直接接 `burned_fees`，**没有列出 Cancun/Prague 引入的 `blob_gas_used`、`excess_blob_gas`、`parent_beacon_block_root`、`requests_hash`**。这与当前主网 header 并不一致。按 EIP 的字面表述，只能理解为「在末尾追加一个字段」，具体插入位置需要以最终实现为准——原文在这一点上表述不严谨。

### 4. 携带证明的交易（Proof-carrying transactions）

原文只有一行：**TBD，严重依赖 ZK L1 的设计**。

**批注**：这是整份 EIP 的「悬念」所在。`PROOF_TX_TYPE` 这个常量已经预留了，说明作者设想的最终形态是：L1 不必真的重执行 L2 区块，而是由某种「携带 ZK 证明的交易」把 `EXECUTE` 的验证成本压下来。但它被显式地推迟到 ZK L1（L1 自身的实时证明化）落地之后。

## 设计理由（Rationale）

- **可编程的「共识层」（Programmable "consensus layer"）**。`EXECUTE` 只负责验证 STF；至于「谁能出块、区块怎么来」，交给 rollup 自己的智能合约去约束。因此 rollup 可以自由选择：限制只有许可制排序器（permissioned sequencer）能提交（换取中心化排序 + 快速预确认 preconfirmation）；或完全开放（基于排序 based sequencing）；或限制在一个质押排序器网络内。也可以把 `coinbase` 固定为 DAO 控制的金库地址（与提议者地址解耦），或按需调整 gas limit / 价格。要点：**保留 rollup 现有的大部分可配置性**。
- **Gas 代币（Gas tokens）**。很多 rollup 为了在 L1 存款时铸造 L2 gas 代币，新增了自定义交易类型。本 EIP **拒绝引入这种复杂度**，改为依赖通用的 L1→L2 消息去「解锁预铸（pre-minted）代币」。副作用是：项目可以自由决定「什么样的 L1 交互触发 L2 gas 代币释放」，**无需改动 EVM 行为**就能天然支持自定义 gas 代币。
- **锚定（Anchoring）**。设计灵感来自 [EIP-4788](https://eips.ethereum.org/EIPS/eip-4788)（把 beacon 区块根暴露给 EVM）：用一笔系统交易把 `bytes32 anchor` 注入 L2 的一个预部署合约。`anchor` 具体是什么由项目自定——L1 状态根、消息根、滚动哈希（rolling hash），或别的东西。
  - **代价**：相比基于自定义交易类型的现有做法，L1→L2 消息在 L2 侧**无法从 L1 发送方推导出 `msg.sender`**，因此依赖 L1 访问控制的合约在 L2 上使用跨链权限时必须改造。作者认为这个取舍可接受，理由是：L2→L1 方向本来就有同样的问题（以太坊本来就不原生知道 L2 的发送方）。
- **Base fee 归集（Basefee collection）**。以太坊销毁 base fee，而多数 rollup 把它收归己有以支撑自己的资金模型。为了在最小改动下支持这个用例，本 EIP 只是**把销毁额通过 header 里的 `burned_fees` 暴露出来**；项目可以选择忽略它（L2 也照样销毁），也可以把这笔金额从「L1→L2 代币托管（escrow）」中记入某个地址，实现 base fee 归集。
- **重执行 vs ZK 证明（Re-execution vs ZK proofs）**：原文 **TBD**，未展开。

## 安全考量（Security Considerations）

**原文为 `TBD`，未写。** 同样为 `TBD` 的还有 **Test Cases**（测试用例）与 **Reference Implementation**（参考实现）。

**向后兼容性（Backwards Compatibility）** 有一段实质内容：现有 rollup 迁移为 native 的难易，取决于其**等价程度（degree of equivalency）**——因为 `EXECUTE` 暴露出来的 STF **不支持自定义操作码（custom opcodes）、自定义预编译（custom precompiles）、自定义交易类型（custom transaction types）**。

**批注**：这一句其实是全文最有杀伤力的约束。它把「谁能成为 native rollup」直接筛掉了一大批：任何做了 EVM 魔改的链（自定义预编译、自定义 tx type、修改过的 gas 表）都不能原样迁移。EIP 把「EVM 等价（EVM-equivalent）」从一句营销词变成了**准入门槛**。同时，前面「blob 交易会触发 `ExecuteError`」的规则，也意味着 L2 内部不能再套一层 blob DA。

## 值得记住的要点

1. **一句话规格**：新增 `EXECUTE` 预编译 → 验证 `state_transition(chain, block)` → 顺带禁掉 blob 交易 → 顺带做一次 anchoring。整份 EIP 的技术核心就这一个函数。
2. **规范成熟度极低**。预编译地址、输入/输出编码、**gas 计费**、安全考量、测试、参考实现，全部 `TBD`。**不要把它当成可实现的规范来读**，把它当成「接口意向书」。
3. **动机是治理与信任，不是性能**。目标是让 rollup 摆脱自建证明系统与自建升级治理，从而真正够到 Stage 2。
4. **两个"顺带"其实是硬约束**：不支持 blob 交易；不支持自定义操作码 / 预编译 / 交易类型。后者决定了哪些现有 L2 迁得过来。
5. **可编程共识层是设计核心的妥协点**：STF 由 L1 固定，但「区块从哪来、谁能出、coinbase 给谁、gas limit 多少」全部留给 rollup 的 L1 合约。这就是「保留差异化」与「统一验证」之间的分界线。
6. **`burned_fees` 是个小而巧的钩子**：只往 header 加一个 uint64，就让 L2 能自由选择「销毁还是归集」base fee——因为 L2 复用同一个 STF，L1 有的它自动就有。
7. **完整版依赖 ZK L1**。`Proof-carrying transactions` 被显式挂起，说明作者心里的终局是「L1 实时证明化之后，`EXECUTE` 靠验证 ZK 证明而非重执行来实现」。在那之前，`EXECUTE` 的经济学（重执行的 gas 成本）是没有答案的。
