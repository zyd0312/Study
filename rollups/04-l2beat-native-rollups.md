# 原生 Rollup：现状与去向（Native Rollups: Where they are, and where they are going）

> **作者**：Conor McMenamin（Nethermind）& Luca Donno（L2BEAT）｜**发表日期**：2025-05-19｜**原文链接**：https://medium.com/l2beat/native-rollups-where-they-are-and-where-they-are-going-cb21eb103d46
> **一句话结论**：把 rollup 的状态转换函数（state transition function）换成以太坊 L1 内置的、与 EVM 等价的 `EXECUTE` 预编译（precompile），rollup 就不再需要自己造和维护一个 VM，也不再需要治理来跟随 L1 升级——执行的安全性直接继承 L1，rollup 只剩下桥、排序、费用这些"自己的事"；但代价是数据可用性（DA）成本、证明者假设和互操作性都还有一堆没解决的问题。

## 背景：这篇文章要解决什么问题

以太坊的扩容路线图经历了几次转向：先是 L1 分片（sharding），然后是 2020 年 Vitalik 提出的「以 rollup 为中心的路线图（rollup-centric roadmap）」——L1 退守到"只把共识和数据可用性这两件事做好"（原文引用 Vitalik 的说法是 "phase 1.5 and done"），把执行扩容全部外包给 L2。

但 2025 年前后，以太坊研究的重心又摆回了 L1 执行扩容。于是出现了一个尴尬的问题：如果 L1 自己就能跑到几千甚至上万 TPS，那 rollup 还有什么意义？以 rollup 为中心的路线图是不是一开始就错了？

这篇文章要做三件事：

1. 讲清楚 **native rollup（原生 rollup）** 到底是什么（核心是 `EXECUTE` 预编译）；
2. 论证它在这个新格局里的定位——为什么 rollup 仍然有价值，以及 native rollup 相比"普通 rollup"和"L1 执行分片"分别多了什么；
3. 诚实列出还没解决的技术难题。

作者明确说这是"用我们自己的话"来讲，属于研究性综述而非规范提案，`EXECUTE` 的细节还会继续迭代。

## 核心内容

### 1. `EXECUTE` 预编译：把 EVM 塞进 EVM

Native rollup 的定义非常紧凑：**它是把自己的状态转换函数替换成 `EXECUTE` 的 rollup**。`EXECUTE` 是一个 L1 上的预编译函数，设计目标是 **EVM 等价（EVM-equivalent）**，并且作为以太坊 EVM 的一部分被维护和升级。原文调侃这叫 "EVM-ception"（EVM 套 EVM）。

最初提案中，`EXECUTE` 接收四个输入：

| 输入 | 含义 |
|---|---|
| `pre_state_root` | 执行前的状态根 |
| `post_state_root` | 执行后的状态根 |
| `trace` | 执行轨迹：一串 L2 交易 + 对应的状态访问证明 |
| `gas_used` | 声称消耗的 gas |

当且仅当以下三条同时成立时返回 `true`：

1. `trace` 是一个格式合法的执行轨迹；
2. 从 `pre_state_root` 出发对 `trace` 做**无状态执行（stateless execution）**，最终得到 `post_state_root`；
3. 这次无状态执行消耗的 gas 恰好等于 `gas_used`。

**关键设计点：`EXECUTE` 不接收任何证明（proof）作为输入。** 这带来了整篇文章里最重要的一个自由度——L1 验证者（validator）可以用两种方式来确信 `EXECUTE` 的调用是正确的：

- **朴素重执行（re-execution）**：验证者自己把 `trace` 重跑一遍。计算量和验证者门槛，与今天通过执行交易来更新状态是同一个量级。
- **验证 SNARK**：验证者去验证一个证明该执行有效的 SNARK。

因为 `EXECUTE` 的接口里没有 proof 这个参数，**共识层不需要"钦定"（enshrine）任何证明系统或电路**。每个质押运营者可以自己选择喜欢的 zkEL 验证器客户端，就像今天大家主观地选择执行层客户端（EL client）一样。原文指出，"要不要把证明系统写进协议"目前社区意见是分裂的——而 native rollup 的这个设计恰好把这个决定推迟了。

> **批注**：这一点是理解 native rollup 全部魅力的钥匙。传统 ZK rollup 必须在链上部署一个 verifier 合约，等于把某一个具体的证明系统（以及它的 bug）焊死进了自己的安全模型。`EXECUTE` 的接口只描述"执行的结果应该是什么"，而不是"你必须用哪种方式说服我"，因此证明系统变成了客户端层面的实现细节，可以像 Geth/Nethermind/Reth 一样多样化和演进。这是 credible neutrality（可信中立性）在工程层面的一次落地。

除了 `EXECUTE`，rollup 还需要一些 rollup 专属的功能：桥接、排序规则、费用、代币治理等。这些不在 `EXECUTE` 覆盖范围内，构成了后文"开放挑战"的主体。

### 2. 为什么需要它：rollup 的"治理困境"

Rollup-centric 路线图有一个从没被真正解决的副作用：**rollup 被迫在"最小化信任但不可升级"和"引入治理以换取可升级性"之间二选一。**

即使是 EVM 等价的 rollup，也**无法随 L1 自动升级**——L1 硬分叉改了 EVM 语义，rollup 必须由某个治理主体（多签、DAO、安全委员会）主动把改动搬过来。这就是为什么几乎所有 rollup 都保留了升级权限，也因此在安全性和中立性上打了折扣，**即使有退出窗口（exit window）也不能完全消除这个问题**。

`EXECUTE` 是打破这个权衡的自然解法：既然状态转换函数就是 L1 的 EVM 本身，那么 L1 分叉时 rollup 就跟着分叉了，**升级无需治理（governance-free upgrades）**。

### 3. 路线图的转向：L1 执行扩容回归

作者接着处理那个尴尬问题：既然研究重心回到 L1 执行扩容，rollup 还有必要吗？他们先问"为什么会转向"，再问"L1 到底能不能扩到 rollup 那个量级"。

**为什么转向？**

- 适度扩容 L1 本身就有明确收益：强制交易（forced transactions）带来的抗审查、互操作性、大规模退出（mass exits）、证明验证等，都依赖一个不太拥堵的 L1。
- 更尖锐的一条：**五年过去了，没有任何一个 rollup 在安全性或中立性上做到了可与 L1 相提并论的水平。** 作者对此比较克制——"rollup 不该被责怪（……或者至少不是所有 rollup 该被责怪）"，因为需要的技术是真的难做。但与其他 L1 的竞争压力，让以太坊倾向于寻找比"完全依赖外部 rollup 团队"更快更安全的路径。这也是过去有人主张搞"由 EF 驱动的、无代币的、上线即 Stage 2 的公共品 rollup"的原因。

**L1 能扩到那个量级吗？**

作者的答案基本是"能"。扩容的本质是利用**执行与验证之间的不对称性**：rollup 用 ZK 处理执行、用 DAS（数据可用性采样）处理数据。没有理由认为这些手段不能直接搬到 L1 上——事实上相关工作已在推进（用 RISC-V 替换 EVM 的长期提案、zkVM 的延迟执行等）。今天的全节点靠下载全部 calldata 并重执行来验证 L1，将来它们会验证 ZK 证明并对 blob 做采样。

### 4. 那 rollup 的增量价值到底是什么

如果 L1 能到几千上万 TPS，rollup 的存在理由被压缩到三条：

1. **时机问题**：以太坊需要扩容的时候（L1 只有 12–13 TPS 真实吞吐），ZK 技术还不成熟。为了避免把不成熟的证明系统钦定进协议，以太坊选择了"自由市场"路线——让 rollup 去试错、去发展技术、去承担某个证明系统选错了的风险。作者认为这**基本上是成功的**：ZK 技术被 rollup 采用后，bug 被大量暴露、迭代速度极快；如今一些路线（比如 zkVM 相对于 zkEVM）正在收敛，可能已接近生产可用，最终可以反哺 L1。
2. **从 1 万 TPS 到 1000 万 TPS，唯一的路是异步执行分片（asynchronous execution shards）**。实现方式要么是 L1 上的内置执行分片（类似 NEAR 的做法），要么就是 rollup。
3. **Rollup 是 L1 的定制扩展和试验田**：Arbitrum、Starknet、Fuel Ignition、Eclipse 各自集成了非 EVM 的虚拟机，各有优势，而这些是以太坊在中短期（甚至可能永远）不可能采纳的。

在这个未来里，L1 的角色是**把这些异质 rollup 社区粘合在一起的、中立且抗审查的胶水**。

### 5. Native rollup 相比"普通 rollup + L1"多了什么：L1 级别的执行安全

主要增量就是那个 EVM 等价的 `EXECUTE`：**它消灭了 rollup 自建、自维护、自升级一套 VM 的需求。** 除了 rollup 专属逻辑之外，`EXECUTE` 替换掉今天各家 rollup 五花八门的状态转换函数。

由此带来的结论非常强：

- **`EXECUTE` 里的 bug，会像 EVM 本身的 bug 一样通过硬分叉来修复。** Rollup 部署者和用户直接接入以太坊的安全性。
- **跟着 L1 一起分叉，就把 rollup 的风险隔离成了纯粹的智能合约风险（smart contract risk）**，极大地缩小了攻防面。
- 次级效应：用户对 rollup 的信心提升、部署 rollup 更容易、开发者资源可以共享。

### 6. Native rollup 相比"L1 执行分片"多了什么：自治权

作者提醒读者：上面那些好处，**如果把以太坊上的 rollup 换成执行分片，几乎一模一样都能拿到**（引用 Vitalik 2024-05-23 的文章）。执行分片把底层链的状态切成若干可以独立处理交易的并行环境，跨分片通过一个协调层来完成，这个协调层看起来会很像今天的 L1 执行层。而且执行分片在以太坊之外已经有落地实现，技术上是可行路径。

那么 rollup 相对分片的差别是什么？**自治（autonomy）**。Rollup 是自治的枢纽，可以自行决定排序、桥接、强制包含、治理、gas 代币等等。更进一步，这种文化上和技术上的独立性，让 rollup 成为 L1 的理想试验田。

原文特意加了个星号注脚：**这是所有 rollup 都能带来的好处，不是 native rollup 独有的。**

> **批注**：把 5、6 两节合起来看，native rollup 的定位就很清楚了：它试图在一个坐标系里同时拿到两个极点的好处——**执行安全性向执行分片看齐（因为执行就是 L1 的 EVM），自治权向普通 rollup 看齐（因为桥、排序、治理仍然自己说了算）**。传统 rollup 是"自治 + 自担执行风险"，执行分片是"L1 执行安全 + 无自治"，native rollup 想要"L1 执行安全 + 自治"。

## 关键术语（中英对照）

| 术语 | 英文 | 含义 |
|---|---|---|
| 原生 Rollup | Native rollup | 用 L1 的 `EXECUTE` 预编译替换自身状态转换函数的 rollup |
| 执行预编译 | `EXECUTE` precompile | 输入 pre/post 状态根、trace、gas_used，验证一段无状态执行是否正确的 L1 预编译；不接收证明作为输入 |
| 派生预编译 | `DERIVE` precompile | 设想中的第二个预编译/功能，用于把 L1 的信号（存款、强制包含、治理）载入 rollup 状态并执行，细节尚未确定 |
| 状态转换函数 | State transition function (STF) | 定义"给定旧状态和一批交易，新状态是什么"的规则；native rollup 把它外包给 L1 |
| EVM 等价 | EVM-equivalent | 与 L1 EVM 语义完全一致（区别于仅"兼容"） |
| 执行轨迹 | Trace | 一串 L2 交易 + 对应的状态访问证明，是 `EXECUTE` 的核心输入 |
| 无状态执行 | Stateless execution | 不持有全量状态、仅凭 trace 中的状态访问证明即可完成的执行 |
| 钦定/内置（证明系统） | Enshrine | 把某个具体证明系统写进共识协议；native rollup 的设计刻意避免了这一点 |
| 无治理升级 | Governance-free upgrades | Rollup 随 L1 硬分叉自动升级，无需多签/DAO 介入 |
| 执行分片 | Execution shards | 把链的状态切成多个可并行独立执行的环境 |
| 数据可用性采样 | DAS / PeerDAS | 节点只抽样下载部分数据即可确信数据可用；与"每个节点都要下载完整 trace"不兼容 |
| 同步可执行 | Synchronously executable | 多个状态上的交易可以在同一时刻/按顺序被执行 |
| 同步可组合 | Synchronously composable | 跨多个执行环境执行一批交易，效果如同它们在同一个执行环境里 |
| 累计执行 gas 上限 | `EXECUTE_CUMULATIVE_GAS_LIMIT` | 限制单个 slot 内所有 `EXECUTE` 可消耗的总 gas，用以约束证明者负担 |
| 利他少数证明者假设 | Altruistic-minority prover assumption | 假设至少有一个无私的证明者会在一个 slot 内为所有 `EXECUTE` 生成证明 |

## 与 2021 年 Deribit 那篇的关系

Deribit Insights 那篇（2021-05）的核心判断是：**ZK Rollup 的致命软肋是 EVM 兼容太难**——通用智能合约在 ZK 电路里做不出来，所以 ZK rollup 当时只能做支付和交易所这类专用应用；而 Optimistic Rollup 靠"能直接跑 EVM 字节码"这一条，吸走了 DeFi 的迁移需求。那篇文章里，"EVM 兼容性"是一个 rollup 团队必须靠自己的工程能力去攻克的护城河。

Native rollup 从根子上改写了这个格局，可以从三个层面看：

1. **"做出 EVM 兼容"这件事本身不再是 rollup 团队的任务。** 2021 年的问题是"我怎么把 EVM 塞进 ZK 电路"；native rollup 的答案是"你别塞了，直接调用 L1 的 `EXECUTE`，EVM 等价性由以太坊协议本身保证"。原本 Deribit 认为是 ZK 阵营最大障碍的那道墙，被移出了 rollup 的责任范围。

2. **ZK 阵营的兼容性劣势不仅被填平，还反转成了优势。** 按 2021 年的叙事，Optimistic Rollup 的优势就是"EVM 语义对齐"。但当 EVM 等价性由 L1 免费提供之后，剩下的差别只剩下"你的执行结果靠什么被确信"。这里 native rollup 依赖的是 L1 验证者的重执行或 SNARK 验证——没有 7 天挑战期，没有欺诈证明的活性假设。原文并没有直接说"OP rollup 输了"（这不是它的论点，不要过度引申），但它给出的价值主张——"执行保证与以太坊本身一样强"——恰好正面覆盖了 Optimistic Rollup 当年赖以取胜的那块地盘。

3. **2021 年那篇没有讨论、而这篇视为核心的问题是"治理"。** Deribit 的框架里，rollup 的风险主要是"欺诈证明能不能被提交"和"电路对不对"。而 2025 年 L2BEAT 的框架里，最大的结构性问题是：**rollup 无法跟随 L1 自动升级，因此必须保留升级权限，因此不可能真正达到 L1 的中立性。** 这个问题在 2021 年还看不见，因为那时几乎没人在意 rollup 的升级钥匙握在谁手里。Native rollup 就是冲着这个问题去的。

> **批注**：也就是说，从 2021 到 2025，行业对"rollup 的核心难题"的定义整个换了一层——从"技术上能不能跑通 EVM"变成了"信任上谁有权改动这套规则"。ZK 那条被 Deribit 判为软肋的路线，反而因为技术成熟（zkVM 收敛）成了 L1 自身的扩容方案候选；而 native rollup 是把这条成熟技术反向内置回 L1，让所有 rollup 都能白嫖。不过要注意：这篇文章通篇的重点不是"ZK 赢了 OP"，而是"执行这件事应该由 L1 统一提供"，两者的问题意识不在同一个层面。

## 开放问题与风险

原文的 "Open Challenges" 是全篇最有价值的部分，作者自己也承认 "Native rollups are a vibe"（原文引用，大意是：目前还停留在氛围阶段）。

### Rollup 专属功能：`EXECUTE` 管不到的那一半

- **本地 rollup 交易**：预期仍由 L1 上的 inbox 合约处理，与今天的 rollup 没有区别。
- **L1 存款/信号与强制包含交易**：这些是 EVM 目前根本不处理的 rollup 专属功能（举例：op-geth 为了处理存款，必须 fork geth）。目前的讨论集中在给 EVM 加一个 **`DERIVE` 预编译/功能**——rollup 在执行前/执行中调用它，把 L1 的信号载入并在 rollup 状态上执行（比如把资产桥进来）。可证明地调用 `DERIVE` 将成为 trace 生成的一部分。**具体细节仍然缺失。** 这里有一个长期设计分歧：
  - 方案 A：只有 rollup 需要调用 `DERIVE`，L1 不需要——L1 与 rollup 互为彼此眼中的独立执行环境。
  - 方案 B：L1 和 rollup 都要调用 `DERIVE`，L1 的状态也被当成一个 rollup 来对待（可能关掉某些 rollup 专属功能）。
- **谁能往 inbox 发交易**：native rollup 被承诺可以完全自定义常规排序（规则、选择）和强制包含，这是 `DERIVE` 的典型用例。
- **状态转换如何被证明**：最初提案是每次 `EXECUTE` 调用都伴随一个链下证明，作为 L1 有效性检查的一部分被验证。为此，**DA 里放的必须是执行轨迹（trace）而不是交易数据**。原文明确说这是"实验性概念，且与 native validium 或 state-diff rollup 不兼容"。好处是：省掉链上重复验证证明的昂贵开销；每个验证者可以跑自己的证明验证器（如同今天的客户端多样性），避免钦定特定证明系统；证明系统的 bug 也不需要硬分叉来修。
- **谁来证明状态转换**：终局形态下，**一个区块要最终确定，就要求这个 L1 slot 里的每一次 `EXECUTE` 都被证明**。最初提案依赖一个很强的假设：所有这些证明都能由某个**利他证明者**在一个 slot 内提供，即系统的安全性建立在"利他少数证明者假设"之上。为了限制这位"利他英雄证明者"的负担，提案引入 `EXECUTE_CUMULATIVE_GAS_LIMIT`，给单个 slot 内所有 `EXECUTE` 可消耗的总 gas 设上限。
- **要不要 rollup 专属的费用**：理论上同样一组交易在任何 rollup 上消耗的 L1 资源应该一样。但每个 rollup 可能通过 `DERIVE` 或智能合约做独特的前处理/后处理（只接受加密交易、按某个权重函数强制排序、强制批量执行……），这些差异要不要反映在费用上，是开放问题。

### Trace 作为 DA 的代价：这可能是最硬的约束

- **优点**：完整 trace + 状态访问证明同时支持无状态重执行和无状态 ZK 证明生成。不钦定任何实现，L1 节点自选 ZK 验证器（可以是同一证明系统的不同实现，也可以是完全不同的证明系统）。多份证明会通过 p2p 网络传播，一批利他的（或间接被激励的）无状态证明者可以为每次 `EXECUTE` 生成并分享证明。
- **致命缺点**：**带状态访问证明的 trace 比交易数据大得多。** 因为每个节点都必须下载完整 trace，这种 DA 形式**与采样（如 PeerDAS）不兼容，导致 `EXECUTE` 无法利用 blob**。结论很直白：**native rollup 的交易费可能显著高于非 native rollup**——不过作者认为"无风险执行的溢价"仍能吸引风险厌恶型用户。
- 三条退路，每条都要付出代价：
  1. **让重执行变成可选**：trace 可以发到 blob 里，只有那些愿意下载全部 blob 的节点才能支持重执行；外部无状态证明者必须属于这一类。
  2. **彻底放弃完整重执行支持，用交易数据替代 trace**：DA 成本可以精确维持在今天的水平。但 trace 不再上链，有状态节点就必须直接生成证明，或者按需产出并分享 trace 给无状态证明者/想重执行的客户端。这样一来，利他证明者（作者假设只有无状态才可能利他）就依赖于这些有状态节点的可用性，**可能损害证明的多样性**。
  3. **更激进：用任意数据承诺替代 trace**，从而支持 native alt-DA L2 和 native state-diff L2。但在 alt-DA 下数据可用性没有保证，**重执行这个最后的兜底手段就没了**，第三方证明者也无法无许可地生成 trace，证明的生成与多样性将完全依赖交易发送方。替代方案是强制要求链上证明——那就自动获得了证明多样性，代价是**又把特定证明系统钦定进协议**（绕回了原点）。

### 互操作性：同步可执行 ≠ 同步可组合

作者把互操作性分成两级：

- **同步可执行（synchronously executable）**：多个状态上的交易能在同一时刻/按次序被执行。这需要跨状态的排序器紧密协调，协调最紧的情况就是所有状态共用同一个排序器。Based sequencing 和 shared sequencing 承诺提供这个能力。**Native rollup 可以通过自定义排序规则，选择性加入与 L1、以及任意多个其他 native rollup 的同步可执行。** 注意：L1、现有 rollup、native rollup 其实都能做到这一层。
- **同步可组合（synchronously composable）**：跨多个执行环境执行一批交易，效果如同它们本来就在同一个执行环境里。这难得多——同步可执行只讲执行的**时机**，不讲被执行的**状态**。同步可组合还需要排序器协调 **加上** "原子最终性技术（atomic finality tech）"：
  1. **能对参与组合的所有状态做 all-or-none 的最终确定**。AggLayer 的做法是搞一个协调层（一个 meta-rollup），由它的执行来决定加入 AggLayer 的各 rollup 的最终性：各 rollup 先按自己的规则临时最终化，真正的最终性要求所有 AggLayer rollup 都已临时最终化且互不冲突（即跨 rollup 记账是合法的）。作者注明：AggLayer 式的互操作性**不**需要共享排序器，但同步可组合**需要**。
  2. **一套数据结构**，让参与组合的 rollup 向协调层申报"我给出的有效输出"和"我期待的输入"。协调层收集这些信号，检查所有输入输出是否两两匹配；匹配则各 rollup 新状态成为最终，否则全部回滚。

  在这个范式下，**协调层完全控制着参与组合的 rollup 在各自桥里的资产**。这给桥合约的安全性压上了很重的担子——但 native rollup 的承诺是：组合双方与协调层的**执行**部分会变得像 L1 执行一样可靠。

- **风险隔离（risk isolation）**：因为 native rollup 是 EVM 等价的，其执行保证与以太坊本身一样强，于是同步可组合的主要风险被压缩成两项：
  - **桥风险**：退化为"审计一个智能合约"，这是 rollup 部署者和用户（理论上）有能力理解的、有边界的风险。
  - **排序器选择风险**：恶意的共享排序器可以向组合中的 rollup 申报不匹配的输入输出，导致这些 rollup 的状态回滚。应对方式包括回退到默认排序器，或干脆关掉可组合性。

### 吞吐量与可组合性的此消彼长

这是文章最后一个、也是相当反直觉的论点：**可组合性会吃掉吞吐量，而且可能吃掉很多。**

把 rollup / 分片当作**异步执行环境**时，把以太坊从 1 万 TPS 的 L1 扩到 100 万+ TPS 的生态是可行的。但一旦引入跨 rollup 的可组合性，吞吐量就掉下来。

作者的算例：一个 L1 + 2 个 native rollup，每个都能跑 1 万 TPS，生态总吞吐约 3 万 TPS。

- 如果两个 rollup 互操作、创建一个临时联合状态，那么**每笔组合交易要在两个状态上都执行一遍**，于是只要发生任何互操作，这两个 rollup 的累计吞吐必然低于 2 万 TPS。乐观情况下大约是 `20k - 组合交易数`。而且在 L1 上协调这个 all-or-nothing 联合状态还会引入额外开销。
- **最坏情况**：跨两个 rollup 的交易依赖太多，联合状态必须单线程执行，累计吞吐直接掉回 1 万 TPS；再加上 L1 上的协调开销（对临时最终化的状态做 back-running），整个以太坊生态的总吞吐会**跌到 2 万 TPS 以下**。

一般规律：**每一对同步组合的执行环境，如果所有交易都有组合依赖，那么这个联合执行环境的吞吐就退化到其中最慢那个环境的量级。** 每一笔跨环境的组合交易，都在削减共享系统的吞吐。

但作者点出关键的一线生机：**rollup 和分片的可组合性是按需（on-demand）发生的，而 L1 是永远可组合的，因此 L1 的吞吐永远被这个上限卡住。** 这构成了 rollup 相对 L1 的一个结构性优势。

由此作者提出一个开放研究方向：**吞吐量与可组合性之间的这个反比关系，值得研究其精确权衡曲线，以及如何高效发现"吞吐 vs 可组合性"的均衡点——比如通过一个市场机制。**

## 值得记住的要点

- **`EXECUTE` 的接口里没有 proof，这是整个设计的支点。** 因为不接收证明作为输入，共识层就不必钦定任何证明系统；验证者可以重执行、也可以各自选择喜欢的 zkEL 验证器客户端，证明系统的多样性和演进被保留在客户端层面。
- **Native rollup 真正卖的不是"更便宜"，而是"无治理升级 + 执行风险隔离"。** Rollup 跟着 L1 一起硬分叉，`EXECUTE` 的 bug 像 EVM 的 bug 一样被修；rollup 剩下的风险退化为智能合约风险。它甚至可能**比现在的 rollup 更贵**（因为 trace 型 DA 不能用 blob），卖的是"无风险执行的溢价"。
- **Rollup 相对执行分片的唯一差别是自治**：排序、桥、强制包含、治理、gas 代币仍归自己。Native rollup = 执行分片级别的执行安全 + rollup 级别的自治。
- **最硬的技术瓶颈在 DA**：完整 trace + 状态访问证明比交易数据大得多，每个节点都得下全量，因此与 PeerDAS 采样不兼容、无法用 blob。三条替代路线（trace 进 blob / 用交易数据 / 任意数据承诺）都会以牺牲重执行兜底、证明者多样性或中立性为代价。
- **终局的安全性建立在"利他少数证明者假设"上**：一个 slot 里的每一次 `EXECUTE` 都要被证明，目前的提案假设有个无私证明者能扛下来，只能靠 `EXECUTE_CUMULATIVE_GAS_LIMIT` 来限制它的负担。这是一个尚未被激励机制解决的问题。
- **可组合性不是免费的**：同步可组合会把联合系统的吞吐拉低到最慢环境的量级。Rollup 之所以还能赢，是因为它的可组合性是按需的，而 L1 是永远可组合、因而永远被吞吐上限锁死的。
